# OnTrack v2.4 — Behavioral Specification & Verification Plan (`SPEC.md`)

**Version:** 2.4  
**Product Source of Truth:** `docs/PRD.md` (v2.4)  
**Technical Design Companion:** `docs/ARCHITECTURE.md` (v2.4)  
**Purpose:** Define **what OnTrack must do for each user** and **how QA proves every requirement works**, independent of internal code structure.

> **Convention for Working Assumptions:** Items marked **[Configurable Assumption]** correspond to provisional policies in `PRD.md` Section 10. They must be driven by server configuration so product policy changes require configuration updates rather than code rewrites.

## 2. Module A — Authentication, Sessions & Access Control (`FR-001`–`FR-004`)

### 2.1 Required Behavior for the User
1. **Registration (`/register`, `FR-001`):**
   - Collects `first_name`, `last_name`, `email`, `username`, and `password`.
   - Displays a live 5-item validation checklist updating on input:
     1. First name: 1–16 characters (non-empty after trim check per UI rule: minimum 1 character, max 16).
     2. Last name: 1–16 characters.
     3. Email: valid email format (max 50 characters) and unique (case-insensitive).
     4. Username: 4–32 characters, English letters only (`^[A-Za-z]{4,32}$`), unique.
     5. Password: 4–16 characters containing at least one lowercase (`a-z`), one uppercase (`A-Z`), one digit (`0-9`), and one special character strictly from `@$!%*?&` (no other characters outside `[A-Za-z0-9@$!%*?&]`).
   - `Sign up` is disabled until all five rules pass.
   - Server re-validates every rule, hashes the password with a salted one-way hash, assigns role `regular`, returns confirmation (`succeed`), and navigates to `/login`.
   - Specific user-readable errors are shown for duplicate username, duplicate email, invalid fields, or server failure.
   - Links to `/login` and `/privacy-and-terms-of-use` are visible, along with textual notice that registration/use constitutes acceptance of terms.
2. **Login (`/login`, `FR-002`):**
   - Collects `username` and `password`; `Sign in` is disabled while either input is empty.
   - Valid credentials create a server-revocable session with configurable lifetime in days, return `{id, username, first_name, last_name, email, user_type}`, and navigate to `/track-map`.
   - Invalid credentials (unknown username OR wrong password) return the exact same message `* Invalid username or password` and reveal `Forgot password? contact support` (`mailto:` link).
3. **Navigation Bar & Session Lifecycle (`FR-003`, `FR-004`):**
   - Immediately upon login (without browser reload), the navbar displays `Hello, <First Name> <Last Name>`, a link on the user's name to `My Tracks`, a separate Admin link iff `user_type == 'system'`, and `Logout`.
   - Reloading the browser with a valid session restores the user state; expired or revoked sessions redirect protected routes to `/login` and reject protected API calls (`401`).
   - Clicking `Logout` revokes the session on the server, clears local client state, and navigates to `/login`. Even if the logout network call fails, local state is cleared and the user is navigated to `/login`.

## 3. Module B — Interactive Map, Hybrid Routing & GPX Export (`FR-005`–`FR-009`, `FR-023`)

### 3.1 Required Behavior for the User
1. **Topographic Map & Geolocation (`FR-005`):**
   - Renders Israel Hiking Hebrew topographic map tiles filling the available viewport.
   - Default center `32.6000, 35.0000`, initial zoom `13`, allowed zoom `7–16`.
   - Requests browser geolocation on load: if granted, places a current-location marker and centers on the user; if denied or unavailable, silently keeps default center with no error message.
2. **Start & Finish Endpoint Selection vs. Edge Rating Mode (`FR-006`, `FR-008`, `FR-021`):**
   - `/track-map` provides an explicit interaction mode toggle: **`Plan Route` (default)** and **`Rate Trails`**.
   - In **`Plan Route` mode**, every map click/tap exclusively controls Start/Finish selection (even when tapping on top of a trail, preventing accidental rating dialogs):
     - Highlights the next required selection label (`Start`, then `Finish`).
     - 1st click/tap places `Start` (car marker) and populates read-only `Start` lat/lng inputs formatted to 3 decimal places while retaining full floating-point precision internally.
     - 2nd click/tap places `Finish` (road marker) and populates read-only `Finish` lat/lng inputs (3 decimals displayed, full precision sent to API).
     - 3rd click/tap clears both endpoint markers, sets a new `Start`, clears `Finish`, highlights `Finish`, and retains any already-drawn route until recalculation or `Clear All`.
   - In **`Rate Trails` mode**, tapping/clicking an `ACTIVE` edge (on the viewport-bounded network layer or on a calculated route's network segments) opens the edge rating dialog without placing or modifying Start/Finish markers. When zoomed out below `NETWORK_LAYER_MIN_ZOOM` (default `12`) or when the viewport edge cap is exceeded, the UI displays a "Zoom in to view and rate trails" hint.
   - `Clear All` is always enabled: removes Start marker, Finish marker, calculated route, AND current-location marker; clears coordinate displays; disables `Create Track` and `Create GPX File`.
3. **Hybrid Route Calculation (`FR-007`, ` PRD §6.2`):**
   - `Create Track` is enabled iff both endpoints are selected AND user is currently entitled (`FR-018`).
   - Clicking `Create Track` shows the global loading spinner (`FR-015`), clears any previous route, and sends full-precision `start_lat`, `start_lng`, `end_lat`, `end_lng` (plus logical `request_id`).
   - Server verifies entitlement, then builds a continuous ordered start-to-finish route:
     - Searches nearest trail-network entry to Start (`CLOSE` radius, then `FAR` radius in meters) and nearest exit to Finish (`CLOSE`, then `FAR`).
     - **Case 1 (Entry & Exit found, connected):** driving access (Start→Entry) + shortest trail-network path (Entry→Exit, undirected; baseline hop-count or configured distance mode, never weighted/filtered by difficulty) + driving exit (Exit→Finish). If Entry == Exit, internal section is empty.
     - **Case 2 (Entry & Exit found, disconnected components):** driving access + driving connector (Entry→Exit) + driving exit.
     - **Case 3 (No Entry found within `FAR`):** external mountain-cycling fallback directly Start→Finish.
     - **Case 4 (Entry found, no Exit within `FAR`):** driving access (Start→Entry) **concatenated with** mountain-cycling fallback (Entry→Finish) — continuous with no gap.
   - If any required external routing call fails, times out, hits quota, or produces a discontinuous route, the server returns an actionable error and **no partial/empty route**; `Create GPX File` stays disabled.
   - Does **not** display total distance, travel time, elevation profile, or overall route difficulty. Route is ephemeral (cleared on browser refresh; never saved to account or shared graph).
4. **Difficulty Coloring & Aggregation (`FR-023`, `PRD §6.4`):**
   - Consistent palette everywhere (planning map, upload preview, admin map):
     - Display Level `1 — Easy`: **Green** (`average_difficulty` in `[1.0, 1.5)`)
     - Display Level `2 — Moderate`: **Orange** (`average_difficulty` in `[1.5, 2.5)`)
     - Display Level `3 — Hard`: **Red** (`average_difficulty` in `[2.5, 3.0]`)
   - Edges default to their initial difficulty (1 for legacy unrated edges, overall upload difficulty for newly created user edges). Explicit reports replace the fallback with their arithmetic mean, rounded only for display. Ingestion never changes existing ratings.
   - Unrated external routing connectors render in a visually distinct neutral style **[Configurable Assumption]**; a persistent legend explains the 3 difficulty levels (and notes that 4x4 passability on external connectors is unverified).
5. **Client-Side GPX Export (`FR-009`):**
   - `Create GPX File` enables only after a route is successfully rendered, and **stays enabled for that displayed route even if eligibility/grace subsequently expires**.
   - Generates valid GPX 1.1 XML in the browser (no server request) with OnTrack metadata, one `<trk>` containing **one `<trkseg>`**, and ordered `<trkpt lat="..." lon="...">` elements; `<ele>` is written iff elevation is a finite number (never quoted, `null`, or `undefined`). Downloads as `route.gpx`.
6. **Map Location Search (`FR-025`, MVP):**
   - Authenticated users (regardless of route-creation entitlement) see a responsive Hebrew/English location search bar on `/track-map` (desktop & mobile).
   - Typing triggers debounced search (canceling stale in-flight requests) via the provider-independent geocoding API and displays selectable results.
   - Selecting a result centers/zooms the map and displays a temporary search marker **without** altering Start/Finish. Explicit `Set as Start` / `Set as Finish` actions (or normal map clicks) let the user adopt the searched coordinates. `Clear All` clears the temporary search marker.
   - Empty results, ambiguous matches, provider outages, and rate/quota limits show clear actionable feedback.
7. **Future-Feature Placeholders (`FR-026`, MVP UI Only):**
   - `/track-map` shows `Save Route` (after route generation), `Add Waypoint` / `Multi-Point Route`, and `AI Route Planner` (whose preview/tooltip also references `Multi-Stop AI Planning`); navbar / `My Tracks` shows `My Routes`. All display "Coming Soon" and trigger zero unfinished backend calls.

## 4. Module C — Administration, Repository Inspection & Batch Ingestion (`FR-010`–`FR-013`, `FR-022`)

### 4.1 Required Behavior for the User
1. **Admin Area (`FR-010`):** Accessible via navbar link to `system` users within the same web application; contains Configuration (`FR-022`), All-Data Repository Map (`FR-011`), Users Directory (`FR-012`), Batch Ingestion (`FR-013`), and Route-Planning Playground.
2. **All-Data Map (`FR-011`):**
   - `Load all tracks` triggers the global spinner and draws all `ACTIVE` repository edges as bold dashed lines (width 6) colored by effective difficulty (`1`–`3`).
   - `Load all points` triggers the global spinner and draws circular markers (radius 4) for `ACTIVE` nodes; clicking/tapping a marker shows its coordinates in a popup.
   - Cached up to 600s and revalidated against graph revision so unchanged reloads avoid re-downloading payloads while any committed geometry or rating change immediately serves updated data; `system` authorization is verified prior to serving cached/`304` responses.
3. **Users Directory (`FR-012`):** Auto-loads a read-only table of registered users showing `ID`, `Username`, `First name`, `Last name`, `email`, `User type` (omitting password hashes and account creation timestamps).
4. **Batch Ingestion (`FR-013`):**
   - `Update Tracks from Cloud` and `Update Tracks from Server local` immediately acknowledge initiation and run asynchronously in the background (rejecting/ignoring duplicate concurrent batch triggers).
   - Scans source files, parses GPX and KML (with `lon, lat` KML coordinate order fixed), skips TWL and unsupported files, preserves endpoints during simplification, snaps nodes and reuses unordered endpoint pairs in the trail network, bumps graph revision, and emails the initiating admin with imported count and elapsed time (or a failure email if processing fails at any stage).
5. **Admin Configuration (`FR-022`):**
   - Displays and updates `MIN_REQUIRED_TRACKS` (integer `>= 1`, default `1`), plus independent positive finite `POINT_SIMPLIFICATION_DISTANCE_M` and `NODE_SNAP_RADIUS_M` (proposed defaults 20 m each), and **[Configurable Assumptions]** `FREE_ROUTE_CREATIONS` (integer `>= 0`, default `1`) and `REJECTED_TRACK_GRACE_PERIOD_HOURS` (number `>= 0`, default `24`).
   - Invalid inputs are rejected leaving stored values untouched; shows success/error feedback; never exposes secrets or API keys.

## 6. Module E — Community Contributions, Overall Upload Difficulty, Edge Rating, Ingestion & Entitlement (`FR-018`–`FR-021`, `PRD §6.3`–`6.6`)

### 6.1 Required Behavior for the User
1. **Two-Step Upload & Validation (`FR-020`):**
   - Authenticated user opens upload modal, picks a file (initial format: GPX), and submits for validation.
   - Server validates untrusted input: configurable size/point limits (build defaults: `MAX_UPLOAD_MB = 10`, `MAX_UPLOAD_POINTS = 50,000`), safe XML structure, valid coordinate ranges (`lat ∈ [-90,90]`, `lon ∈ [-180,180]`), and `>= 2` distinct points in at least one validated segment. All `<trk>` and `<trkseg>` elements are parsed in order while keeping disconnected `<trkseg>` segments separate (no artificial connecting line).
   - Invalid files show an actionable message, allow picking a replacement file, and grant zero credit.
   - Valid files create a server-owned `DRAFT` (zero credit) and render a map preview inside the modal. Canceling or abandoning a draft grants zero credit.
2. **Overall Difficulty and Independent Edge Rating (`FR-021`):**
   - User must choose one overall difficulty (1–3, no default). Preview uses that color; no per-portion editor.
   - After ingestion, an authenticated user can switch `/track-map` to **`Rate Trails` mode** and select an `ACTIVE` edge from the viewport-bounded network layer or from a calculated network route, even without route creation entitlement (proposed policy), without triggering Start/Finish placement. Display effective difficulty, count and own rating; accept one editable explicit rating per user/edge, update color on success, no upload credit. External edges cannot be rated.

3. **Durable Acceptance & Asynchronous Processing (`FR-018`, `FR-020`, `PRD §6.5`–`6.6`):**
   - Confirming saves the immutable file/reference, overall difficulty (referencing server-owned draft geometry), `PENDING` state, and durable processing obligation atomically, returning `202 Accepted` immediately without waiting for graph stitching.
   - Submission states & credit:
     - `DRAFT`, `REJECTED` → **0 credit**, not in shared network.
     - `PENDING`, `PROCESSING`, `RETRY`, `TECHNICAL_FAILED` → **1 provisional credit**, not in shared network.
     - `ACTIVE` → **1 permanent credit**, visible in shared network.
   - Same-user duplicate file across credit-bearing states does not award extra credit; confirmation and worker execution are idempotent.
   - Worker reduces points, snaps retained points to nearest nodes within the configured radius (including newly inserted nodes), skips self-loops, reuses unordered node pairs, initializes only new edge difficulty and publishes ACTIVE changes atomically. No geometric overlap matching or edge splitting. Measure topology risks in POC.
4. **Entitlement, Grace & Free Allowance (`FR-018`, `PRD §6.5`):**
   - `qualifying_count = count(distinct user submissions in PENDING, PROCESSING, RETRY, TECHNICAL_FAILED, ACTIVE)`.
   - `contribution_eligible = qualifying_count >= MIN_REQUIRED_TRACKS`.
   - **Rejection Grace [Configurable Assumption]:** If a definitive business rejection drops `qualifying_count` from `>= MIN_REQUIRED_TRACKS` to `< MIN_REQUIRED_TRACKS`, existing active sessions of that user retain grace until `min(now + REJECTED_TRACK_GRACE_PERIOD_HOURS, session_expiry)` (ended early by logout/revocation; non-transferable to new logins; non-extendable by retries/refreshes).
   - **Free Route Allowance (confirmed default `0`, configurable via FR-022):** Lifetime per-account `FREE_ROUTE_CREATIONS` (default `0`, disabling free usage cleanly until raised by an administrator) is consumed **only** when enabled (`> 0`) and neither `admin_exempt`, `contribution_eligible`, nor valid grace applies. A successful logical route creation is finalized by **atomic server-side settlement before the HTTP response is transmitted** (the server cannot guarantee client receipt of the HTTP packet). Retries of the same logical request within the replay window recover the stored temporary response without charging again; failed calculations consume zero allowance; concurrent requests cannot exceed remaining allowance; in-flight entitlement/session changes are reevaluated before settlement (`ARCH` §4.10).
5. **Personal Page — `My Tracks` (`FR-019`) & Community Contribution Levels (`FR-024`):**
   - Displays only the current user's non-draft submissions (`filename`, `submitted_at`, `status`, `credit_state`, and user-friendly rejection reason or technical-delay notice — never raw exceptions), plus `qualifying_count`, `MIN_REQUIRED_TRACKS`, free allowance remaining, and active `grace_until`. Polls while submissions are in flight; shows upload CTA when empty or rejected.
   - **Contribution Level (`FR-024`):** Derived strictly from `ACTIVE` submissions only (`0–5` Explorer, `6–9` Adventurer, `10–19` Trailblazer, `20+` Trail Master), persisted across sessions, displayed with a distinct visual badge/icon in the navbar (next to user's name) and on `My Tracks` along with total `ACTIVE` count and remaining `ACTIVE` tracks needed for the next level (`Trail Master` displays total count with no next-level target). Independent of provisional route credit, roles, routing, and edge-rating weights. Includes `My Routes` ("Coming Soon") placeholder (`FR-026`).
